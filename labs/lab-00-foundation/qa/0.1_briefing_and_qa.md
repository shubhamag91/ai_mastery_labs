## Part 1: The briefing

### 1. Goal
We'll build the `shopai` Python package that every later lab adds to. It starts empty, but set up properly. There's no AI in this task. It teaches three concepts:
- **54 Project structure & dependencies:** one package, a lockfile, and an environment anyone can recreate exactly.
- **55 Configuration & secrets:** settings come from the environment, and secrets never go into git.
- **56 Structured logging:** each log entry is one line of JSON, so you can search and count logs like data.

### 2. Why it matters
In analytics, a notebook that works on your machine is usually enough. Production code also runs on other people's laptops, on CI servers and in Docker containers on Cloud Run. Three things go wrong most often there:
- Library versions drift, and code that worked last month breaks.
- Secrets leak into git.
- Logs are too hard to read when something breaks at 2am.

This task adds a guard against each one, and later labs rely on them. Lab 1.P's LLM client reads its API key from config, Lab 3.P's CI runs `make test`, and Lab 6.P's deployment reads secrets from the environment.

### 4. How
- **uv** installs Python, creates the virtual environment, adds libraries and writes the lockfile. It's one fast tool that replaces pip, venv and pip-tools.
- **`src/` layout:** the code lives in `src/shopai/` rather than at the top of the repo, so tests import the installed package, not whatever files happen to be in the folder.
- **ruff** is a linter, which flags likely bugs and style problems. It's also a formatter, which rewrites code into one consistent style.
- **pytest** runs the tests.
- **pydantic-settings** reads environment variables and `.env` into a typed Python object. If a required setting is missing, it fails at startup instead of halfway through a run.
- **structlog** writes each log event as JSON, with fields you choose, such as `model=...` or `tokens=512`.
- **pre-commit** runs checks every time you `git commit` and blocks the commit if a check fails.
- **gitleaks** scans what you're about to commit for anything that looks like an API key or password.
- **make** gives longer commands short names, so `make test` means the same thing on your laptop and in CI.

### 5. New terms
- **Package:** a folder of Python code you can install and import by name (`import shopai`).
- **Virtual environment (`.venv`):** a folder of libraries installed for this project only, so they can't clash with other projects.
- **Lockfile (`uv.lock`):** a record of the exact version of every library, including the libraries those libraries depend on.
- **Dev dependency:** a tool you need while developing the code, like ruff or pytest, but not to run it.
- **Environment variable:** a named setting passed to a program, such as `ANTHROPIC_API_KEY`. The `.env` file holds them locally.
- **Git hook:** a script git runs at a set moment, for example just before a commit.
- **JSON lines:** one JSON object per line, so each log entry can be filtered like a row in a table.

### 6. Who does what

### Q2. What does a virtual environment do?

**The problem.** When you write `import pandas`, Python looks through a list of folders for a folder called `pandas`. You can see the list with `python3 -c "import sys; print(sys.path)"`. Without a virtual environment, that list points to one shared library folder, `site-packages`, used by every project on your machine. That causes two problems:
- If project A needs pandas 1.5 and project B needs pandas 2.2, installing one breaks the other.
- Nothing records what each project actually needs. Code works because of whatever happens to be installed.

**What a venv is.** It's just a folder:

```
.venv/
├── bin/python                      → a link to a real Python interpreter
├── lib/python3.12/site-packages/   → this project's libraries, and only these
└── pyvenv.cfg                      → a note saying where the base Python lives
```

When you run `.venv/bin/python`, it looks in `.venv`'s own `site-packages` instead of the shared one. That's the whole trick: a separate shelf of libraries, plus a Python that knows to look on that shelf. Nothing is virtualised the way a virtual machine is.

**"Activating"** a venv (`source .venv/bin/activate`) only puts `.venv/bin` at the front of your shell's `PATH`, so typing `python` finds that one first. `uv run <command>` does the same for a single command without activating anything. That's why you'll see `uv run pytest` rather than plain `pytest`.

**Venv vs. lockfile.** The lockfile is the recipe and the venv is the dish.
- `.venv/` is never committed. It's large and specific to your machine.
- `uv.lock` is committed. Anyone, including GitHub Actions or a Docker build, runs `uv sync` and gets an identical venv.
- If your venv ever gets into a strange state, delete it and run `uv sync` again. It's meant to be thrown away.

If you've used conda environments, it's the same idea. conda also isolates non-Python things like C libraries and CUDA; a venv only isolates Python libraries.

**Isolation comes in layers:**

| Layer | What it isolates | First used |
|---|---|---|
| venv | Python libraries | 0.1 |
| Docker container | the whole OS: Python itself, system libraries, files | 4.P (Postgres), 5.P (your API) |
| Cloud Run | the machine: CPU, memory, network | 6.P |

### Q3. Why do most projects have a `src/` folder?

There are two common layouts:

```
flat layout                    src layout
repo/                          repo/
├── shopai/                    ├── src/
│   └── config.py              │   └── shopai/
├── tests/                     │       └── config.py
└── pyproject.toml             ├── tests/
                               └── pyproject.toml
```

**The trap it prevents.** When you run Python or pytest from the repo root, Python adds the current folder to its search list from Q2.
- **Flat layout:** `import shopai` finds the `shopai/` folder sitting right there, whether or not the package installs correctly. Your tests pass. Then the Docker build installs the package properly, and a missing file or an undeclared dependency crashes it in production. The tests checked your folder, not what you shipped.
- **src layout:** there's no `shopai/` at the root to find by accident. `import shopai` only works through the installed package, so the tests check what actually ships. A production crash becomes a failure on your laptop.

**"Installed" doesn't mean copied.** uv installs your own package in *editable* mode: the venv holds a pointer to `src/shopai/`, not a copy. When you edit a file, the change takes effect immediately, with no reinstall.

**Two smaller reasons:**
- The root of this repo holds `labs/`, `data/`, `docs/`, `tests/`, `import_issues.py` and a `Makefile`. `src/` makes it obvious which part is the product.
- Scripts at the root, like `import_issues.py`, can't accidentally be imported as if they were part of the package.

The flat layout also works, and plenty of projects use it. The src layout is what `uv init --package` creates and what the official Python packaging guide recommends.

### Q4. What goes in `config.py`, and shouldn't it sit at the root?

**What's in it.** About 15 lines. This is a sketch; the real file was built during the task:

```python
from functools import lru_cache
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")

    anthropic_api_key: SecretStr   # required: no default, so startup fails without it
    log_level: str = "INFO"        # optional: falls back to the default
    environment: str = "local"     # local, ci or production

@lru_cache
def get_settings() -> Settings:
    return Settings()
```

- **The class lists every setting the app accepts**, each with a type and an optional default. It doubles as documentation: one place shows everything you can configure.
- **Where each value comes from:** first a real environment variable, then the `.env` file, then the default. Names match regardless of case, so `anthropic_api_key` reads `ANTHROPIC_API_KEY`. Real environment variables take priority because Cloud Run has no `.env` file and passes values through the environment.
- **Types are checked.** Suppose you add `max_retries: int = 3` and someone sets `MAX_RETRIES=three`. The app refuses to start, with a clear error, instead of crashing an hour into a batch job.
- **`SecretStr`** prints as `**********`. To use the real key you have to call `.get_secret_value()` on purpose, so a stray `print(settings)` or log line can't leak it.
- **`@lru_cache` on `get_settings()`** means the settings are read once and the same object is reused after that. Tests can clear the cache and swap in fake values.

**Why not at the root?** It helps to separate two things:
- **Config values** (`.env` and `.env.example`) do live at the root. They describe this copy of the repo on this machine.
- **Config code** (`config.py`, which reads those values) is part of the program, so it lives in the package with the rest of the program.

A rule of thumb for the whole repo:
- **The root** holds files *about the repo*: how to build, test and run it (`pyproject.toml`, `Makefile`, `.pre-commit-config.yaml`, `.env.example`).
- **`src/shopai/`** holds the *product*.
- **The Docker image** gets the product and the lockfile, nothing else.

If `config.py` sat at the root, it wouldn't be part of the installed package. It would work on your laptop, because the root is on Python's search path when you run from there. In Docker it would fail with `ModuleNotFoundError: No module named 'config'`, which is exactly the trap from Q3. Inside the package, every module imports it the same way: `from shopai.config import get_settings`.

Some projects also keep a `config/` folder of YAML files at the root for large, non-secret settings such as model parameters. That's a valid pattern, but this project doesn't need it yet.

### Q5. The software engineering fundamentals behind 0.1

Every tool in this task exists because of a principle. The tools change every few years; the principles don't.

#### 5.1 Reproducibility: same inputs, same result, anywhere
A program's behaviour depends on four things: **code, dependencies, configuration and data**. Reproducibility means pinning down all four:

| What | How it's pinned |
|---|---|
| Code | git |
| Dependencies | the lockfile |
| Configuration | the settings class |
| Data | Labs 0.2 to 0.P (spec, fixed random seed, contract tests) |

- **Version numbers.** Most libraries use *semantic versioning*, `MAJOR.MINOR.PATCH`, for example pandas `2.2.3`. A patch fixes bugs, a minor version adds features, and a major version may break your code.
  - In `pyproject.toml` you write the *range* you'll accept, such as `pandas>=2.2`.
  - The lockfile records the *exact* version that was chosen.
- **Transitive dependencies.** In 0.1 you add about five libraries, and they bring in their own dependencies. For example, pydantic-settings needs pydantic, which needs pydantic-core and others. The lockfile pins all of them. Many "it worked last week" failures come from a library you've never heard of publishing a new version.

It's the same question a model validator asks: can someone else re-run this and get the same numbers?

#### 5.2 Keep configuration out of the code
The same code runs on your laptop, in CI and in production. What differs between them is **configuration**: which API key, which database, how detailed the logs are. Configuration comes from the environment, never from the code. This is rule III of the *Twelve-Factor App*, a widely used checklist for cloud services.

A quick test: could you make the repo public right now without leaking anything? If so, configuration is properly separated. It's the same as moving a model from dev to UAT to production without editing the code; the environment tells it which database to use.

Two rules follow from this:
- **Secrets are configuration with extra rules.** They never go in git, logs or Docker images. Locally they live in `.env`; in the cloud they live in Secret Manager.
- **Fail fast.** Check configuration at startup and refuse to run if it's wrong. A clear error in the first second is far cheaper than a crash after 400 paid API calls.

#### 5.3 Catch problems early ("shift left")
A problem costs more the later it's found:

```
editor → commit → CI on GitHub → staging → production → a customer notices
(seconds, free)                                  (incident, apology, fix under pressure)
```

Each tool in 0.1 moves a check further to the left of that line:
- ruff flags an undefined variable while you type.
- The pre-commit hook is there to stop secrets at the moment you commit.
- `make test`, and from Lab 3.P CI too, catches a broken function before it's merged.

Production engineering is largely about stacking several cheap checks so that no single one has to be perfect. Banks call this layered controls: maker-checker, reconciliations, audit.

#### 5.4 Automate anything people do inconsistently
People forget steps and argue about style; tools don't.
- **Formatter.** Code style is decided once, by the tool. Nobody debates spacing in code review, and diffs show only real changes.
- **Linter.** It catches code that is valid Python but almost always a bug, such as an unused import, a variable used before it's defined, or a bare `except:` that silently swallows every error.
- **Makefile.** Each routine gets one name. `make test` runs exactly the same command on your laptop and in CI, so "it passes for me" actually means something. A newcomer can read the Makefile to learn how to work in the repo.

#### 5.5 Tests make change cheap
A test is a small program that runs your code on a known input and checks the output, in three steps:
1. **Arrange:** set up the input.
2. **Act:** call the function.
3. **Assert:** check the result.

The value isn't proving the code is right today. It's being able to change the code next month and know within seconds whether you broke something.

**Why start with a trivial test?** It proves the plumbing works: pytest finds the tests, the package imports, and `make test` runs. It's like checking a pipeline end to end on a one-row table before loading the real data.

The kinds of check this curriculum builds, from cheapest to most expensive:

| Kind | What it checks | Speed and cost | First in |
|---|---|---|---|
| Unit test | one function, using a fake instead of a paid API | milliseconds, free | 0.1 |
| Data contract test | the data still contains what the labs need | seconds, free | 0.P |
| API test | the HTTP endpoints | seconds, free | 5.P |
| Eval | output quality from a real model | minutes, costs money | 3 |

#### 5.6 Observability: seeing what a running program did
Once code runs on a server, you can't step through it in a debugger. What it records is your only evidence. There are three kinds of record:
- **Logs:** what happened, event by event.
- **Metrics:** counts and rates over time.
- **Traces:** the path of one request through many steps (Lab 3.4).

Structured logging is where an analytics background helps:
- **A prose log line** like `Called model, took 2.3s, 512 tokens` is only for reading.
- **A JSON line** like `{"event": "llm_call", "model": "...", "latency_s": 2.3, "tokens": 512}` is a row in a table. You can load a day of them into pandas and ask for average latency by model, or errors per hour.

**Log levels** sort events by importance:
- DEBUG: detail for diagnosing problems.
- INFO: normal events.
- WARNING: something unusual that was handled.
- ERROR: something failed.

Production usually records INFO and above, and you switch on DEBUG while investigating. That's what `log_level` in the settings is for. In banking terms, it's an audit trail: who did what, when, and with which inputs, searchable afterwards.

#### 5.7 One source of truth
Settings are read in one module, and logging is set up in one module. Everything else imports from them. To change how logs look or add a setting, you edit one file, and two parts of the app can never disagree. It's like having one governed definition of "active customer" instead of five slightly different SQL versions across reports.

#### 5.8 Version control habits
- **Work on a branch, not `master`.** `master` should always work. A branch is a safe place for unfinished work, and later it becomes a pull request that CI checks before it's merged.
- **Make small commits with clear messages.** One logical change per commit, so the history reads as a record of decisions and any one change can be undone on its own.
- **Use `.gitignore`.** It lists what git must never track: secrets (`.env`) and anything that can be regenerated (`.venv/`, `__pycache__/`, caches).

#### Which principle each 0.1 file serves

| File | Principle |
|---|---|
| `pyproject.toml` + `uv.lock` | Reproducibility |
| `src/shopai/` layout | Test what actually ships |
| `config.py` + `.env.example` | Configuration out of the code; fail fast |
| `log.py` | Observability; one source of truth |
| `.pre-commit-config.yaml` | Catch problems early; automate |
| `Makefile` | Automate; one name per routine |
| `tests/` | Safety net for change |

### Q6. `.venv` vs `.env`: what's the difference?

The names are one letter apart, which makes them easy to mix up. They do completely different jobs.

| | `.venv/` (virtual environment) | `.env` |
|---|---|---|
| **What it is** | a folder of installed libraries: pandas, pydantic, structlog… | a small text file of settings |
| **Question it answers** | "Which libraries can this project import, and which versions?" | "How should this project behave on this machine?" |
| **Example contents** | `.venv/lib/python3.12/site-packages/pydantic/` | `ANTHROPIC_API_KEY=sk-...`<br>`LOG_LEVEL=INFO` |
| **Who creates it** | uv | you |
| **Committed to git?** | no, because it can be rebuilt | no, because it holds secrets |
| **Read by** | Python, when you `import` | `config.py` |

In one line: the venv holds **code** (other people's libraries) and `.env` holds **settings**.

### Q7. What is the lockfile? (explained another way)

**An analogy from analytics work.** Suppose a report's SQL says `FROM customers`, the live table. If you re-run it next month, you get different numbers, even though nobody touched the SQL, because the table changed underneath it. If it instead says `FROM customers_snapshot_2026_10_11`, you get the same numbers every time, on any machine.

- **`pyproject.toml` is like `FROM customers`.** It says "I need pydantic-settings, version 2.5 or newer." What that installs depends on the day.
- **`uv.lock` is the snapshot.** It says "on the day this was set up, exactly these versions were chosen."

**What happens over time:**

1. **Today** you run `uv add pydantic-settings`. uv picks the newest version that fits. That library needs others (pydantic, pydantic-core, python-dotenv…), so uv picks exact versions for those too. It writes every one of them into `uv.lock`, and you commit that file.
2. **Three months later,** GitHub Actions or a Docker build installs the project:
   - **Without the lockfile,** uv picks the newest versions again. Maybe pydantic-core has had a new release that behaves differently. Your code breaks, and nobody changed your code.
   - **With the lockfile,** `uv sync` installs exactly what's in `uv.lock`: the same versions you have, down to the last library.
3. **Upgrading becomes a deliberate choice.** The lockfile changes only when you run `uv add` or `uv lock --upgrade`. The change shows up in `git diff`, so you can see exactly which versions moved, review it, and undo it if it breaks something.

**What's inside the file:** one entry per library, written by uv. You never edit it by hand.

```toml
[[package]]
name = "python-dotenv"
version = "1.1.1"
wheels = [{ url = "https://files.pythonhosted.org/...whl", hash = "sha256:a1b2..." }]
```

The `hash` is a fingerprint, the same idea as the checksum used to verify the uv download. Each library gets one. If a download doesn't match its fingerprint, uv refuses to install it.

**How the files connect** (the version numbers are made up for illustration):

```
pyproject.toml   "pydantic-settings, 2.5 or newer"        you write it     committed
      │  uv lock
      ▼
uv.lock          "pydantic-settings 2.11.0,               uv writes it     committed
                  pydantic 2.12.3, ... + fingerprints"
      │  uv sync
      ▼
.venv/           the installed library files              uv builds it     NOT committed

.env             ANTHROPIC_API_KEY=..., LOG_LEVEL=INFO    you write it     NOT committed
                 (settings: separate from the chain above)
```

**Restated (learner's words):** "venv is used to store libraries and the version that will be used to run the project. uv.lock prevents versions getting changed with time."
