## Key ideas
- **#1 Tokens:** a token is not a word — the tokenizer (byte-pair encoding, trained mostly on English) merges common English fragments into single tokens, but rarely-seen text (romanized Hindi, punctuation stuck to a word) falls back to small fragments, costing far more per word. [1.1](NOTES.md#11-build-a-token-and-context-window-inspector)
- **#1 Tokens:** a model can't inspect the letters inside its own token — it's an opaque ID. The only reliable way it can count letters is to regenerate the word as new text that happens to tokenize near one-letter-per-token (spelling it out), and it will do this even against an explicit instruction not to, unless you also remove its room to do so. [1.1](NOTES.md#11-build-a-token-and-context-window-inspector)
- **#2 Context window / memory:** there is no server-side conversation memory in the API — `messages.create` is stateless. "Memory" is entirely your own code resending the growing message list every turn. Drop the list, and the model has no way to know the conversation happened. [1.4](NOTES.md#14-manage-conversation-state-and-send-an-image)
- **#2 Context window:** cost and context usage grow with the *entire* resent history every turn, not just the newest message — measured 29 → 1,426 input tokens over a 10-turn conversation. [1.4](NOTES.md#14-manage-conversation-state-and-send-an-image)
- **#3 System vs. user prompt:** position matters, but content and format instructions don't degrade the same way. Burying an instruction mid-document left the *content* task intact (the model still found and executed it via attention) but broke the *format* constraint (sentence-count limit, no extra sections) — a thin, low-redundancy signal that gets deprioritized once it's not in the position models weight most heavily. [1.3](NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task)
- **#4 Temperature & sampling:** `temperature` was removed from the SDK's typed interface entirely on current-generation thinking-by-default models (Sonnet 5.5, Opus 5.5) — "effort" replaced it as the main dial. It's still live on non-thinking-by-default models like Haiku 4.5. [1.2](NOTES.md#12-run-a-temperature-and-non-determinism-experiment)
- **#5 Non-determinism:** `temperature=0` held 100% stable across every test we ran, including a review deliberately engineered to be a 50/50 tie, across 80 trials. `temperature=1.0` did destabilize that same tied review (70% agreement). Temperature only has visible effect where the model's own probability distribution is genuinely spread out — it doesn't manufacture uncertainty that isn't there. [1.2](NOTES.md#12-run-a-temperature-and-non-determinism-experiment)
- **#6 Hallucination:** a fluent, confident-sounding answer can still contain a fabrication. The cheap model (Haiku 5.5) invented an "expected Monday, arrived Thursday" framing that the source ticket never stated — a real factual error dressed in natural prose, not a style difference from the correct answer. [1.3](NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task)
- **#7 Model selection:** the capable model's ~40× cost premium bought real correctness on a task built around deliberately unreliable text (it caught contradictions the cheap model missed or misrepresented) — but on a task without that kind of planted ambiguity, the premium likely buys nothing measurable. Judge model choice per task, not in the abstract. [1.3](NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task)
- **#8 Extended thinking:** on current models, thinking has no real "off" state — every run showed nonzero thinking tokens even when `thinking` was never set. Raising `effort` from default to `high` cost more (+4%) with no measurable quality gain on a reading-comprehension task; effort pays off on tasks needing genuine multi-step reasoning, not extraction. [1.3](NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task)
- **#8 Extended thinking:** a small `max_tokens` doesn't make answers more concise — it can truncate mid-reasoning and produce a broken, partial answer instead of a complete one, because thinking tokens compete with visible-answer tokens for the same budget. Seen three times independently ([1.1](NOTES.md#11-build-a-token-and-context-window-inspector), [1.3](NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task), [1.4](NOTES.md#14-manage-conversation-state-and-send-an-image)).
- **#53 Multimodal input:** an image costs meaningfully more than comparable text — one product photo (673 tokens) costs more than 4× a full customer review (150 tokens). Images also get downscaled server-side before tokenizing: a 57×-larger image (by pixel count) cost only 7× more tokens, not a linear scale-up. [1.4](NOTES.md#14-manage-conversation-state-and-send-an-image)
- **#57 Testing LLM code:** dependency injection — taking the SDK client as a function parameter instead of constructing it inside — is the entire mechanism that makes LLM code unit-testable without mocking frameworks, network access, or spending money. Proved directly: the full test suite (75 tests) passes in under a second with `ANTHROPIC_API_KEY` unset and `ANTHROPIC_BASE_URL` pointed at a closed port. [1.P](NOTES.md#1p-build-the-shared-llm-client)
- **#56 Structured logging:** one shared `call()` function means every model call across every script now logs one JSON line (`model`, `input_tokens`, `output_tokens`, `thinking_tokens`, `cost_usd`, `latency_s`) instead of each script measuring and printing these fields its own way, or not at all. [1.P](NOTES.md#1p-build-the-shared-llm-client)

## Rules of thumb
- Use `count_tokens` before any production rollout to estimate cost on real sample text — don't guess from word count, especially for non-English or code-mixed content.
- Use `temperature=0` whenever a classification or extraction step needs to be reproducible/auditable; don't assume it's already the default.
- Don't force a model to answer in a single token/no-reasoning-shown mode on a task it needs to "think through" (letter counting, careful extraction) — it will either silently use a famous-example shortcut (memorization) or visibly fail mid-recovery if you remove its room to reason.
- Budget `max_tokens` generously on any thinking-enabled model, especially for vision calls — a too-small ceiling truncates mid-reasoning, not mid-sentence of a complete answer.
- When evaluating model choice, measure on the task's actual hard cases (planted ambiguity, contradictions), not generic examples — cheap and expensive models can look identical on easy inputs.
- Put every model call behind one shared function that takes the client as a parameter. It's what makes unit tests free and instant, and it's what makes a pricing or logging change a one-line edit instead of a hunt across every script.

## Real-world uses
- **Customer support triage (e-commerce/retail):** classify incoming tickets by theme/urgency at `temperature=0` for reproducibility, reserving the capable model for tickets that are long, contradictory, or otherwise hard to summarize reliably — exactly what [1.3](NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task) measured.
- **Multi-turn support/sales chatbots (any industry):** understanding that memory is pure resent-history bookkeeping is what lets you design compaction/summarization strategies before a long conversation's context cost balloons — directly what [1.4](NOTES.md#14-manage-conversation-state-and-send-an-image)'s token-growth curve demonstrates.
- **Insurance claims / warranty photo review:** sending a damaged-item photo and getting a structured damage assessment, as in [1.4](NOTES.md#14-manage-conversation-state-and-send-an-image)'s damaged-kettle test, which matched the ground-truth label without any hinting.
- **Don't use it for:** precise character-level counting or editing tasks (letter counts, exact substring positions) without independently verifying the output — the model's only strategy is regenerating text as a workaround, which is fragile under constraints and not a substitute for actual string operations in code.

## Hackathon shortcut
Default to the cheapest model at `temperature=0` for anything structured/classification-shaped; only reach for the expensive model where you've actually seen the cheap one fail on a hard case. Skip tuning `effort`/thinking settings unless you're doing genuine multi-step reasoning — it rarely pays off on simple extraction and just adds latency/cost.

## Quiz yourself
1. Why is a token not a word? What kinds of text produce far more tokens than you'd guess from the word count, and what does that do to your bill?
   <details><summary>Answer</summary>The tokenizer (BPE) merged common English fragments into single tokens because they were frequent in training data. Numbers, names, code, and non-English text (especially romanized or code-mixed) were rarely seen in that form, so they fall back to small subword or near-character fragments — more tokens per word, more cost and context-window usage for the same information. Measured: 1.85 tokens/word for plain English vs. 2.63 for a code-mixed review, with one word costing 14 tokens alone. See <a href="NOTES.md#11-build-a-token-and-context-window-inspector">NOTES.md §1.1</a>.</details>

2. Does `temperature=0` guarantee identical output? If a categorization is unstable across runs, is that the model's failure or the prompt's?
   <details><summary>Answer</summary>Not mathematically guaranteed (floating-point non-associativity in GPU batching is a theoretical source of drift), but in every test run here — including a review deliberately engineered to be a 50/50 tie, across 80 trials — it held 100% stable. If a categorization is unstable, check temperature first: it's more likely the actual driver than the prompt's wording, since prompt-level ambiguity alone couldn't destabilize <code>temperature=0</code> even when deliberately engineered to. See <a href="NOTES.md#12-run-a-temperature-and-non-determinism-experiment">NOTES.md §1.2</a>.</details>

3. Where did the extra cost of the larger model actually buy you something, and where was it wasted?
   <details><summary>Answer</summary>Bought something: correctly catching three planted contradictions in a deliberately unreliable ticket — the cheap model missed them and fabricated a plausible-sounding but false reconciliation. Wasted: raising <code>effort</code> to "high" cost 4% more with no quality gain on this reading-comprehension task — effort pays off on genuine multi-step reasoning, not extraction. See <a href="NOTES.md#13-compare-models-prompts-and-thinking-modes-on-one-task">NOTES.md §1.3</a>.</details>

4. Where does a chatbot's "memory" actually live? Why does each turn cost more than the last?
   <details><summary>Answer</summary>Entirely in your own code's message list — the API itself is stateless and has no memory between calls. Each turn costs more because the *entire* growing history is resent and billed as input tokens every single call, not just the newest message. Measured: 29 → 1,426 input tokens over 10 turns. For a 100-turn conversation, this means the later turns become dramatically more expensive purely from history size — motivating summarization/compaction strategies before that happens. See <a href="NOTES.md#14-manage-conversation-state-and-send-an-image">NOTES.md §1.4</a>.</details>

5. What happens to an oversized image's token count, and why?
   <details><summary>Answer</summary>It doesn't scale linearly with pixel count. A 57×-larger image (by pixel count) cost only 7× more tokens (4,757 vs. 673). The API downscales an oversized image server-side before tokenizing it, capping the cost — which also means sending an unnecessarily huge file doesn't buy the model proportionally more visual detail. See <a href="NOTES.md#14-manage-conversation-state-and-send-an-image">NOTES.md §1.4</a>.</details>

6. Why wrap an SDK at all? What would you lose by wrapping too much of it?
   <details><summary>Answer</summary>Wrapping centralizes logging, cost tracking, and testability in one place instead of four slightly different copies — a pricing or logging change becomes a one-line edit instead of a hunt across every script. Wrapping too much (trying to re-expose every SDK feature before anything needs it) adds a translation layer with no payoff: every new SDK capability would need a matching wrapper feature before it could be used, and bugs can hide in either layer. The actual wrapper here only covers the parameters Lab 1's scripts used, plus one escape hatch (<code>extra_body</code> passthrough) for raw fields the typed SDK doesn't expose. Proven directly: the full test suite (75 tests) passes with no API key and no reachable network, in 0.71 seconds — because the client is injectable, not hardcoded inside the wrapper. See <a href="NOTES.md#1p-build-the-shared-llm-client">NOTES.md §1.P</a>.</details>
